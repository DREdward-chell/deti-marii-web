# Разработка в монорепозитории

## Совместная работа

Работайте в коротких ветках по законченным сценариям. Перед разделением задачи согласуйте DTO, состояния, маршрут API и владельца данных. Изменение общего контракта сопровождайте изменениями обоих клиентов и соответствующими проверками.

При работе с AI давайте ему архитектуру, актуальный контракт и конкретную область изменения. Не создавайте вторую реализацию бизнес-правил в боте или интерфейсе.

## Бэкенд

- JDK 25, Gradle Wrapper, Kotlin и Spring Boot закреплены в сборке.
- Код организован по предметной области, не по общим папкам `controllers/services/repositories`.
- JPA-сущности не возвращаются напрямую из API. Используйте отдельные DTO и валидацию входных данных.
- На границе сценария определяйте транзакцию и правила доступа. Проверяйте право на конкретный объект, а не только роль.
- Денежные значения в текущем кейсе не нужны. Длительность участия в будущем храните целым количеством минут; моменты времени — UTC с явно определённой зоной мероприятия.
- Межмодульные зависимости проверяются `ArchitectureTests` и при запуске приложения. Обучение находится в `learning`, оформление и допуски — в `onboarding`; обзор координатора не хранит их как второй источник истины.

Аккаунты и профили сейчас используют `JdbcTemplate` с тем же DataSource и менеджером транзакций, что и реестр событий. JPA starter доступен, но JPA-сущностей в этих модулях нет. Владельца анкеты получайте через публичный `identity.CurrentAccount`: `accountId` из клиентского запроса не является основанием доступа.

## Межмодульные события

Публикуйте события через `ApplicationEventPublisher` внутри транзакции сценария. Для сохраняемых асинхронных реакций используйте `@ApplicationModuleListener`. Реестр публикаций уже подключён к PostgreSQL; отдельный брокер для этих реакций не нужен.

Обработчик должен допускать повтор: используйте стабильный идентификатор события и уникальное ограничение для результата обработки, когда появится первый рабочий подписчик. Не отправляйте сетевые запросы в транзакции исходного бизнес-действия. Событие без транзакционного подписчика не сохраняется как журнал аудита.

Контракты событий размещайте в именованном интерфейсе `events` модуля-источника. Разрешайте подписчику конкретную зависимость, например `onboarding :: events`; внутренние реализации при этом остаются закрытыми. Учитывайте совместимость уже записанных событий при изменении класса, payload или идентификатора обработчика.

Повтор незавершённых публикаций при старте настроен для одного экземпляра backend. Периодические повторы, очистка истории и очередь доставки пока не реализованы; их добавление входит в первый сценарий уведомлений.

## Миграции

Все миграции: `backend/src/main/resources/db/migration`. В репозитории есть версии `V1`–`V9`; следующая свободная версия — `V10__...sql`. Координируйте номера перед объединением веток.

Применённую миграцию не редактируйте: создайте следующую. Таблицы квалифицируйте схемой, например `volunteers.volunteer_profile`. Hibernate работает в режиме `validate` и не создаёт таблицы за Flyway.

Общая БД позволяет использовать внешние ключи и транзакции между схемами. Доступ к данным в коде сохраняет границы модулей. Автоматическое создание пользовательских данных и реальные контакты в миграции не включаются.

`public.event_publication` — служебная таблица Spring Modulith, её схема также управляется Flyway. Автоматическое создание таблиц со стороны Modulith отключено. При обновлении его версии сверяйте формат реестра и проверяйте обновление существующей БД, а не только запуск на пустой базе.

## Фронтенд

Один npm workspace `@deti-marii/frontend`, один корневой lockfile. Все команды установки выполняются из корня репозитория. После изменения зависимостей коммитьте `package.json` и `package-lock.json` вместе.

Общие вызовы API находятся в `src/shared/api`. По мере реализации добавляйте папки функциональных областей в `src/features`. Не переносите правила допуска и вместимости на клиент: он отображает результат серверной проверки.

Запросы идут на относительный `/api/v1/...`. В разработке их проксирует Vite, в полном стеке — Caddy. Локальный CORS и отдельные URL для production-сборки не требуются.

Клиент `shared/api/client.ts` перед каждым изменением получает свежий CSRF-токен с сохранением cookie; это учитывает смену токена при входе и выходе. Не повторяйте изменяющий запрос автоматически после ошибки авторизации. При `409` сохраняйте черновик в форме и предлагайте явно загрузить актуальную версию. Список запросов и примеры — в [контракте API](api.md).

## Конфигурация и проверки

Секреты хранятся в `.env` и исключены из Git. `.env.example` содержит только пример конфигурации. Тесты используют синтетические данные и отдельную PostgreSQL Testcontainers. Они не должны молча пропускаться при отсутствии Docker.

Полный Compose включает `FORWARD_HEADERS_STRATEGY=native` только для приватного backend за Caddy. При прямом локальном запуске обработка forwarded-заголовков отключена. `platform.auth.requests-per-minute` (по умолчанию 30 на IP) задаёт общий лимит регистрации, входа, проверки и повторной отправки кода; счётчик хранится в памяти одного процесса.

## SMTP и сотрудники

Настройки рабочего SMTP задаются через `.env`: `MAIL_ENABLED=true`, `MAIL_FROM`, `SMTP_HOST`, `SMTP_PORT`, `SMTP_USERNAME` и `SMTP_PASSWORD` (пароль приложения). Для STARTTLS обычно используются порт `587`, `SMTP_AUTH=true`, `SMTP_STARTTLS=true`, `SMTP_SSL=false`; для implicit TLS — порт `465`, `SMTP_SSL=true`, `SMTP_STARTTLS=false`. Фактические параметры предоставляет выбранный провайдер. Секреты не коммитятся. В базовом Compose Mailpit отсутствует и отправка по умолчанию выключена; вход волонтёров продолжает работать, а сотрудник без доставки кода получает `503`.

Локальный запуск со сборкой: `docker compose -f compose.yaml -f compose.mailpit.yaml up --build -d --wait`. Для локальной JVM запустите только почту (`docker compose -f compose.yaml -f compose.mailpit.yaml up -d mailpit`) и задайте процессу `MAIL_ENABLED=true`, `SMTP_HOST=localhost`, `SMTP_PORT=1025`, `SMTP_AUTH=false`, `SMTP_STARTTLS=false`, `SMTP_SSL=false`, `MAIL_FROM=noreply@example.test`. Веб-интерфейс Mailpit — `http://localhost:8025`, SMTP — `127.0.0.1:1025`. Почта хранится только в песочнице, без relay.

Роль назначается существующему аккаунту: `bash scripts/coordinator-access.sh grant EMAIL OPERATOR`; отзыв: та же команда с `revoke`. Обе команды увеличивают `security_version`, тем самым отзывая старые сессии, и пишут аудит в одной транзакции. Не добавляйте публичный API назначения роли или рабочие учётные записи в миграции. Пароль сотрудника не передаётся этому скрипту.

Коды привязаны к сессии, хранятся пять минут в памяти и пропадают после рестарта. Повторная отправка требует ещё действующую незавершённую проверку; после истечения срока или пяти ошибок нужно начать вход с пароля. При недоступной SMTP-доставке нет fallback-входа и вывода кода в логи. Код подтверждает вход сотрудника, но пока не отмечает email волонтёра как верифицированный при регистрации.

Основание: [Spring Boot Mail](https://docs.spring.io/spring-boot/reference/io/email.html), [локальный Docker-образ Mailpit](https://mailpit.axllent.org/docs/install/docker/).

Перед передачей изменений: `make check`. При изменении Dockerfile или маршрутизации дополнительно запустите полный Compose-стек и проверьте интерфейс, API и readiness.

Форматирование фронтенда и документации: `npm run format`. Kotlin и Java следуют `.editorconfig`; отдельный Kotlin-линтер пока не подключён.
