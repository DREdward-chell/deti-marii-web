# Архитектура прототипа

## Решение

Одно приложение Spring Boot, один PostgreSQL, один React-интерфейс. Предметные модули разделены пакетами; допустимые зависимости заданы через Spring Modulith в `package-info.java`. Telegram — будущий адаптер внутри приложения.

Это исходная архитектура команды, а не утверждённые бизнес-правила фонда. Порядок допуска, возможность отклика до подготовки, резерв и правила подтверждения часов ещё нужно согласовать.

## Модули

- `identity`: учётные записи, способы входа, роли и привязки аккаунтов. Конфигурация безопасности находится в `internal`.
- `volunteers`: профиль, контакты, интересы, навыки, предпочтения.
- `onboarding`: материалы, прохождение подготовки, допуски к видам помощи.
- `opportunities`: задачи, мероприятия, роли, требования и вместимость.
- `participation`: отклики, решения, отмены, фактическое участие, подтверждённое время. Использует публичные интерфейсы `volunteers`, `onboarding`, `opportunities`.
- `coordination`: ответственный, история взаимодействий, задачи и следующий шаг. Использует публичные интерфейсы предметных модулей.
- `notifications`: задания доставки, повторы, каналы. Будущие подписчики реагируют на устойчиво сохранённые события.
- `adapters`: Telegram и другие внешние входы. Преобразуют сообщения в вызовы публичных сценариев. Не обращаются к чужим репозиториям.
- `system`: публичная техническая информация о приложении.

Для каждого предметного модуля зарезервирована одноимённая PostgreSQL schema. Миграции всех модулей находятся в одной последовательности Flyway. Таблицы, бизнес-сущности и межмодульные контракты будут добавлены в следующих изменениях.

## Правила границ

Публичные интерфейсы модуля размещаются в корневом пакете модуля; реализации и JPA-модели — в `internal`. Новый межмодульный вызов требует явного изменения `allowedDependencies` и проверки архитектурного теста. Циклы запрещены. Наличие общей БД не разрешает изменять чужие таблицы из другого модуля.

REST-контроллеры соответствующего сценария могут жить внутри своего модуля. `adapters` нужен для внешних интеграций, а не для переноса туда всей бизнес-логики.

## Будущая модель

`VolunteerProfile`, `TrainingCompletion`, `Eligibility`, `Opportunity`, `OpportunityRole`, `Application`, `Participation`, `CoordinatorTask`.

Учётная запись не равна профилю волонтёра. Подготовка не равна допуску. Подтверждённый отклик не равен явке. Отсутствие отметки не означает неявку. Планируемые часы не включаются в подтверждённый вклад.

При подтверждении отклика проверка мест, смена состояния и постановка уведомления должны быть одной транзакцией. Сетевые запросы к Telegram выполняются после её завершения. Для доставки понадобится transactional outbox с повторными попытками; в текущем каркасе очередь ещё не реализована. Асинхронные события в памяти не считаются надёжной доставкой.

## Контракт каркаса

`GET /api/v1/system/info` возвращает имя и версию приложения:

```json
{ "name": "volunteer-platform", "version": "0.1.0-SNAPSHOT" }
```

`GET /actuator/health/readiness` возвращает готовность приложения с проверкой PostgreSQL, без внутренних деталей. Остальные маршруты закрыты конфигурацией Security. Генерируемый пароль Spring отключён пустым `UserDetailsService`; вход пока отсутствует. CSRF-защита сохранена для будущей авторизации через cookie.

## Следующие законченные сценарии

1. Профиль волонтёра, вход и роли.
2. Возможность с ролями, требованиями и ограничением мест.
3. Подготовка, отклик и решение координатора.
4. Привязка Telegram и уведомление через outbox.
5. Отмена, фиксация фактического участия и часов.
6. Рабочее пространство координатора и объяснимый подбор.

Порядок допуска и резерв не следует закреплять в модели до уточнения правил фонда.
