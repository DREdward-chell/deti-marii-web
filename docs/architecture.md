# Архитектура прототипа

## Решение и текущий этап

Одно приложение Spring Boot + Kotlin, один PostgreSQL, один React-интерфейс. Предметные модули разделены пакетами; допустимые зависимости заданы через Spring Modulith в `package-info.java`. Деплой — Docker Compose и Caddy. Telegram будет адаптером этого же приложения.

После уточнения требований обучение выделено в `learning`, а `onboarding` отвечает за вступление, оформление и допуски. Количество уроков и сроки хакатона не задают ограничений модели.

Реализованы границы модулей, схемы БД, постоянное хранение публикаций событий, регистрация и собственная анкета волонтёра (2А), чтение анкет координатором и двухэтапный вход сотрудников по email (2Б), рассмотрение и следующий шаг в кабинете волонтёра (3А), ручное подтверждение оформления и допуски к видам помощи (3Б). Добавлен учебный движок с версиями, двумя интерактивными механиками, прогрессом и проверкой оформления (4А). Добавлен каталог возможностей с черновиками, публикациями и доступом после оформления (5А). Медиа, материалы фонда, запись на занятия и уведомления о событиях появятся отдельными этапами. Описанные ниже обязанности — целевая модель, а не утверждение о готовности всех сценариев. [План реализации](implementation-plan.md).

## Владельцы данных

| Модуль          | Ответственность                                                                                      |
| --------------- | ---------------------------------------------------------------------------------------------------- |
| `identity`      | Учётные записи, способы входа, сессии, роли сотрудников и привязки аккаунтов                         |
| `volunteers`    | Профиль человека, контакты, интересы, навыки, регулярность и предпочтения                            |
| `onboarding`    | Рассмотрение анкеты, знакомство, результат пробы, подтверждение оформления и допуски к видам помощи  |
| `learning`      | Учебные маршруты, версии материалов, задания, попытки и прогресс                                     |
| `opportunities` | Возможности помочь, конкретные занятия, роли, требования, места и правила записи                     |
| `participation` | Отклики, подтверждение участия, отмены, явка и подтверждённое время                                  |
| `coordination`  | Задачи координатора, история контактов, вопросы и ответы, следующий шаг, обзор данных других модулей |
| `notifications` | Задания доставки, попытки, результаты отправки и настройки уведомлений                               |
| `adapters`      | Telegram и другие внешние входы, вызывающие публичные сценарии                                       |
| `system`        | Публичная техническая информация о приложении                                                        |

Для восьми предметных модулей от `identity` до `notifications` выделены одноимённые PostgreSQL schema. У `adapters` и `system` собственных бизнес-таблиц нет. Служебные таблицы Flyway и реестра публикаций находятся в `public`.

Миграции идут одной последовательностью: `V1` создаёт исходные схемы, `V2` добавляет `learning`, `V3` — реестр публикаций, `V4` — аккаунты, роли и профили, `V5` — версию безопасности аккаунта, ограничение отправки кодов и аудит выдачи прав, `V6` — рассмотрение и историю его изменений, `V7` — оформление, справочник видов помощи, допуски и их историю, `V8` — учебные маршруты, версии, аудит действий, прохождения и попытки, `V9` — возможности помощи, опубликованные снимки и аудит. Применённые миграции сохраняются неизменными.

## Границы и направление зависимостей

Публичные интерфейсы модуля размещаются в корневом пакете; реализации, репозитории и JPA-модели — в `internal`. Чужие таблицы и сущности недоступны через обход публичных интерфейсов. Контроль границ выполняется архитектурным тестом и при запуске приложения.

Текущие разрешения в `allowedDependencies`:

- `identity`, `system`: без зависимостей на другие предметные модули.
- `volunteers` → `identity`: `CurrentAccount` определяет владельца собственного профиля, `AccountContacts` предоставляет email для карточки координатора.
- `notifications` → `identity`: реализует порт `LoginCodeSender`; правила проверки кодов остаются в `identity`.
- `onboarding` → `volunteers`, `identity`: ссылки на профили через `VolunteerProfiles`, автор решения через `CurrentAccount`, отображение авторов координатору через `AccountContacts`.
- `learning` → `volunteers`, `onboarding`, `identity`: собственный профиль, актуальное оформление и автор редакторских действий.
- `opportunities` → `onboarding`, `identity`: актуальное оформление и допуски, метаданные видов помощи через `VolunteerRoleReader`, автор редакторских действий.
- `participation` → `volunteers`, `onboarding`, `learning`, `opportunities`.
- `coordination` → `volunteers`, `onboarding`, `learning`, `opportunities`, `participation`.
- `adapters` → все предметные модули.

Это разрешённые направления, а не уже существующие вызовы. `learning` читает актуальное оформление через `VolunteerClearanceReader`; ограничения по отдельным видам помощи пока не подключены. `onboarding` не зависит от учебного движка: завершение урока само не меняет оформление или допуск. Координаторский обзор собирает оба набора фактов через публичные интерфейсы. `opportunities` проверяет оформление для каталога, а будущий `participation` будет проверять условия конкретной записи.

Для будущих подписчиков событий добавляем узкий именованный интерфейс `events` в модуле-источнике и разрешаем зависимость вида `onboarding :: events`. Пока предметных подписчиков нет; у `notifications` открыта только зависимость для SMTP-порта авторизации. Общего пакета со всеми событиями и общей бизнес-логикой не создаём.

Синхронные проверки условий действия выполняются через публичные методы модулей. Побочные реакции — через сохраняемые события. REST-контроллеры сценария могут жить внутри его модуля; адаптеры не дублируют бизнес-правила. Изменение `allowedDependencies` сопровождается проверкой отсутствия циклов.

## Независимые состояния и доступ

Отдельно моделируем:

- учётную запись и профиль волонтёра;
- рассмотрение обращения и договорённости о знакомстве;
- подтверждение оформления с автором, временем и историей изменений;
- допуск к конкретному виду помощи;
- прохождение конкретной версии учебного материала;
- отклик, согласованное участие и фактическую явку;
- следующий контакт и добровольную паузу в участии.

Один общий `VolunteerStatus` не заменяет эти факты. Подготовка не подтверждает оформление, а оформление не даёт доступа ко всем сведениям фонда. Отсутствие отметки о явке не означает неявку. Планируемые часы не включаются в подтверждённый вклад.

Права проверяются на сервере для конкретного объекта и действия, включая выдачу файлов. Для решения о доступе используются актуальные факты, а не отстающая проекция координаторского обзора или старое сообщение в боте. Роль сотрудника и этап вступления волонтёра не смешиваются.

Если фонд подтвердит пробу до оформления, приглашение на неё должно быть отдельным разрешённым сценарием с ограниченным набором сведений. Оно не открывает весь каталог. Линейный порядок «курс → созвон → проба → документы» пока не закрепляется в коде.

## Обучение и возможности участия

Реализованный `learning` хранит черновик маршрута и неизменяемые опубликованные версии в JSONB. У урока есть устойчивый UUID и один из типов: `READ`, `SINGLE_CHOICE`, `ORDERING`. Черновик может быть неполным, публикация требует заполненных уроков и корректного ключа проверки. Тексты выводятся как обычный текст, без HTML. Размеры ограничены: до 40 уроков и 8 вариантов в задании; эти защитные ограничения не задают учебную программу фонда.

Одно прохождение закреплено за парой «волонтёр + опубликованная версия». Шаги открываются последовательно; чтение подтверждается действием, выбор и порядок проверяет сервер. Неправильный ответ сохраняется с обратной связью и допускает повтор. Прогресс считается по уникальным успешно завершённым урокам, завершение маршрута записывается отдельно. Интересы и предпочтения не оцениваются как ответы. Обучение не меняет оформление, допуски или роли аккаунта.

Сохранение черновика использует оптимистическую ревизию. Публикация и снятие с публикации блокируют запись маршрута; ответы блокируют сначала маршрут, затем прохождение. Это сериализует ответы с изменением публикации. UUID запроса ответа и уникальное ограничение предотвращают двойную запись при повторе, а тот же UUID с другим содержимым даёт конфликт. Создание прохождения идемпотентно по уникальной паре профиля и версии. Каталог, отдельное прохождение и прогресс координатора читаются в транзакции `REPEATABLE_READ`: число завершённых уроков и дата завершения относятся к одному снимку БД, даже если параллельно сохраняется последний ответ. Редакторские действия записываются в `course_action` с автором и временем; опубликованные версии и попытки остаются в БД. История содержимого неопубликованных правок пока не хранится.

Доступные аудитории: все волонтёры с анкетой либо только с подтверждённым оформлением. Каждое чтение, начало и ответ, включая повтор, проверяют актуальное оформление через публичный порт `onboarding`. Для старого прохождения учитываются одновременно его аудитория и аудитория текущей публикации: ужесточение закрывает старый маршрут, а новая открытая версия не раскрывает старые закрытые материалы. Снятие с публикации закрывает все версии для волонтёров. Проверка оформления выполняется при запросе; уже отданный браузеру текст нельзя отозвать, а при следующем отказе интерфейс очищает загруженный материал. Запись решения об оформлении и учебный ответ не используют общую межмодульную блокировку.

Проекция волонтёра исключает ключ правильного ответа; варианты передаются в порядке UUID, не в авторском порядке. Для ещё недоступных шагов возвращаются только заголовки и типы. Координатор получает прогресс через публичный `CourseManagement`, без прямого доступа к чужим таблицам. Каталог и попытки пока загружаются целиком: пагинация и агрегированные запросы нужны перед ростом объёма данных. Файлы, видео, ограничения по видам помощи и обязательность тем отложены до следующего этапа и согласования материалов.

В этапе 5А `opportunities` хранит описание возможности и отдельные неизменяемые публикации в JSONB, с ревизией черновика и аудитом. Редакторские операции блокируют одну запись возможности; точные повторы не создают новых версий. Справочник видов помощи остаётся в `onboarding`: публичный `VolunteerRoleReader` возвращает метаданные по ID или набору ID, без выдачи права на просмотр других ресурсов. Каталог, подробности и варианты фильтра проверяют актуальное оформление и читаются в `REPEATABLE_READ`. Поиск и пагинация применяются к опубликованным снимкам в PostgreSQL. Собственный допуск отображается как отдельный факт, без автоматической записи или оценки готовности. В карточках нет персональных контактов и данных подопечных; их не следует добавлять в свободный текст.

В `opportunities` различаем постоянную возможность помогать и конкретное занятие с датой и составом. В `participation` отклик на занятие имеет собственный жизненный цикл и не смешивается с обращением о вступлении в фонд. Режим записи и обязательные условия задаются явно; ручное подтверждение каждого отклика пока является предложением команды.

`coordination` хранит свои задачи, контакты и вопросы, но не копирует оформление или учебный прогресс как второй источник истины. Внутренние заметки сотрудника отделяются от сообщений, видимых волонтёру. Личный кабинет должен быть доступен без подключения Telegram.

## Постоянное хранение событий

Подключён `spring-modulith-starter-jdbc`: Spring Modulith Event Publication Registry хранит публикации в `public.event_publication`. Он использует тот же DataSource и транзакцию, что и бизнес-изменение, в том числе при использовании JPA. Созданием таблицы управляет Flyway; автоматическая инициализация Modulith отключена.

Событие публикуется внутри транзакции сценария. Для каждого зарегистрированного транзакционного подписчика реестр сохраняет публикацию. Подписчики с `@ApplicationModuleListener` выполняются асинхронно после commit, в собственной транзакции; асинхронная обработка включена в приложении. При rollback публикация исчезает вместе с основным изменением.

Успешная обработка отмечается завершённой (`completion-mode: update`); ошибка оставляет публикацию для повтора. Повтор через `FailedEventPublications` проверяется интеграционным тестом. Включён также повтор незавершённых публикаций при старте — это настройка для текущего развёртывания с одним экземпляром backend. Перед добавлением нескольких экземпляров её нужно пересмотреть. Периодические повторы, лимиты попыток и очистка завершённых записей будут добавлены вместе с первым рабочим подписчиком.

У реестра есть важные границы:

- Событие без зарегистрированного подписчика не становится постоянной историей предметной области. История решений и аудит проектируются отдельно.
- Обработчик может получить событие повторно. Идемпотентность обеспечивается в сценарии обработчика, а не обещанием «ровно один раз» со стороны транспорта.
- Сохраняемые события содержат идентификатор события, время и минимально необходимые данные. Файлы, секреты и полные анкеты в payload не включаются.
- Класс и структура сериализованного события, а также идентификатор подписчика являются контрактами для повтора. Их изменение требует учёта уже сохранённых публикаций.

Будущий `notifications` преобразует событие в устойчивое задание доставки. Сетевой запрос к Telegram не входит в исходную бизнес-транзакцию. Реестр публикаций уже подключён; очередь доставки, Telegram-клиент и расписание напоминаний ещё не реализованы. Успешная отправка не означает прочтение или согласие человека.

Основание: [события Spring Modulith](https://docs.spring.io/spring-modulith/reference/events.html), [конфигурация и схемы JDBC](https://docs.spring.io/spring-modulith/reference/appendix.html).

## Учётная запись и собственная анкета

`identity.account` хранит нормализованный email и хеш пароля, `identity.account_role` — роли. При регистрации сервер назначает только `VOLUNTEER`; публичного управления ролями нет. Пароли хешируются PBKDF2-HMAC-SHA256 с индивидуальной солью и 600 000 итераций; префикс формата позволяет менять алгоритм в будущем.

Spring Security хранит аутентификацию в серверной HTTP-сессии. При входе меняются идентификатор сессии и CSRF-токен. Cookie — `HttpOnly`, `SameSite=Lax`, с `Secure` в HTTPS-развёртывании. Все изменяющие запросы требуют CSRF, включая регистрацию, вход и выход. Клиент не хранит пароль или токен входа в localStorage. Сессия истекает после 30 минут бездействия; перезапуск единственного backend требует повторного входа. Постоянное хранение сессий пока не подключено.

Для регистрации и входа действует общий лимит 30 запросов в минуту на IP в памяти одного backend. Compose включает native-обработку forwarded-заголовков Tomcat за Caddy; backend не имеет публичного порта, Caddy по умолчанию заменяет входящие forwarded-значения. При другой топологии нужно явно пересмотреть доверенные прокси. Распределённый лимитер и защиту по аккаунту следует добавить перед масштабированием.

`volunteers.volunteer_profile` связан с аккаунтом уникальным `account_id`. Сервис получает его через `CurrentAccount`, а не из тела или URL запроса. Профиль создаётся при первом сохранении; регистрация не создаёт пустую карточку. Поля анкеты пока предварительные, до получения примеров фонда.

Сохранение — полный `PUT` с номером версии. Уникальное ограничение исключает два профиля на один аккаунт, условное обновление по версии защищает от потери изменений между вкладками. Повтор с теми же нормализованными полями возвращает текущий результат без новой версии; устаревший запрос с другими значениями получает `409`. Аккаунты и профили используют JDBC-репозитории и транзакции общего DataSource.

Роли проверяются при HTTP-запросе и на сервисах. На каждом аутентифицированном запросе `AccountSessionFilter` сверяет роли и `security_version` с БД. Изменение роли или версии инвалидирует сессию; сам факт добавления роли к уже открытой сессии не даёт новых прав. Операторский скрипт назначения/отзыва роли координатора меняет версию в той же транзакции и пишет `identity.staff_access_audit`. Значение имени оператора задаёт вызывающий скрипт; это операционный журнал, а не независимая аттестация личности администратора.

## Вход сотрудников и чтение анкет

Роли `COORDINATOR` и `ADMIN` требуют дополнительного кода после пароля. До его проверки в сессии нет аутентификации и доступ к бизнес-данным закрыт. Шестизначный код генерируется `SecureRandom`, действует пять минут, привязан к HTTP-сессии и допускает пять попыток. В памяти хранится HMAC кода с ключом процесса и случайным идентификатором проверки; в ответах API и логах код отсутствует. При повторной отправке прежний код в этой сессии заменяется. Перезапуск приложения сбрасывает незавершённый вход.

Ограничение отправки — одно письмо в минуту на аккаунт — проверяется атомарным обновлением PostgreSQL и действует между браузерами. Общий лимит запросов на IP также охватывает проверку и повторную отправку. Параллельная проверка одного кода может успешно завершиться только один раз. При изменении прав во время ожидания письма проверка отклоняется.

Доставка выполняется через `identity.LoginCodeSender`, реализацию которого предоставляет `notifications`. Отправка SMTP синхронная, с ограниченными таймаутами и вне транзакции БД; ошибка доставки не открывает доступ. Очередь, повторы фоновых уведомлений и подписчики событий ещё не реализованы. По умолчанию отправка отключена; локальный Mailpit включается отдельным Compose-файлом. При подключении реальной почты нужно проверить доставку и настройки TLS у выбранного провайдера.

Email-код добавляет шаг подтверждения, но его независимость от пароля зависит от защиты почтового ящика. Он не является защитой от фишинга; TOTP/WebAuthn остаются возможным следующим усилением для сотрудников. [Рекомендации OWASP по MFA](https://cheatsheetseries.owasp.org/cheatsheets/Multifactor_Authentication_Cheat_Sheet.html).

`coordination` читает данные через публичный `volunteers.VolunteerDirectory`. Список возвращает краткие карточки с пагинацией, поиском по имени и фильтром регулярности; подробная карточка включает email из публичного `identity.AccountContacts`. Контроллер, каталог и сервис контактов требуют роль координатора и серверный признак завершённого входа `STAFF_VERIFIED`. Прямые обращения к чужим таблицам не добавлены. Чужая анкета остаётся доступной только для чтения.

## Рассмотрение обращения (3А)

`coordination` вызывает публичный `onboarding.ReviewWorkflow`. Данные принадлежат `onboarding`: `review` хранит текущую версию, `review_revision` — неизменяемые снимки результата, сообщения, следующего шага, внутренней заметки, автора и времени. Веб-API не предоставляет удаления или редактирования истории. Последние 50 снимков возвращаются координатору; остальные остаются в БД. Email автора подставляется из текущего аккаунта, а его неизменный ID записан вместе с решением.

Состояния `NEW`, `IN_REVIEW`, `CONTINUE`, `PAUSED`, `DECLINED` относятся только к знакомству. Порядок не зафиксирован, автоматических переходов и назначения допусков нет. Следующий шаг необязателен; если он задан, обязателен ответственный (`VOLUNTEER` или `COORDINATOR`), дата необязательна. Дата — календарный день без времени и часового пояса, а не запись в календаре.

Запись блокирует одну строку рассмотрения, проверяет версию клиента и добавляет новую ревизию с обновлением указателя в одной транзакции. Конкурентное первое создание тоже сериализуется. Повтор идентичного нормализованного состояния не создаёт историю; отличающаяся устаревшая правка получает `409`. Чтение не создаёт строк: для ещё не рассмотренной анкеты возвращается `NEW`, версия `0`.

Собственный маршрут определяет профиль через `VolunteerProfiles.ownId()`. Ответ собирается явной проекцией: без внутренней заметки, автора, номера версии и истории. Изменение доступно только координатору после кода и со свежим CSRF. Сохранение сразу делает публичную часть видимой в кабинете; уведомление по почте или в Telegram пока не отправляется.

Основание: [управление сессиями Spring Security](https://docs.spring.io/spring-security/reference/servlet/authentication/session-management.html), [CSRF](https://docs.spring.io/spring-security/reference/servlet/exploits/csrf.html), [хранение паролей OWASP](https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html), [Spring Boot за прокси](https://docs.spring.io/spring-boot/how-to/webserver.html), [заголовки Caddy](https://caddyserver.com/docs/caddyfile/directives/reverse_proxy).

## Оформление и допуски (3Б)

Публичные интерфейсы `onboarding.ClearanceWorkflow` и `VolunteerRoleCatalog` обслуживают кабинет координатора. Данные остаются в `onboarding`: `paperwork` и `paperwork_revision` хранят ручное подтверждение оформления; `role_admission` и `role_admission_revision` — независимые решения по парам «профиль + вид помощи». Как и рассмотрение, решения записываются вместе с историей в одной транзакции с блокировкой своей строки и проверкой версии клиента. Первое конкурентное создание сериализуется; повтор идентичного состояния не добавляет ревизию.

Оформление имеет состояния `NOT_CONFIRMED`, `CONFIRMED`, `NEEDS_UPDATE`. Допуск — `NOT_GRANTED`, `GRANTED`, `SUSPENDED`, `REVOKED`. Подтверждение документов не меняет допуски; выдача, приостановка и отзыв допуска не меняют документы, рассмотрение и роли `identity`. Готовность к роли может быть отмечена до оформления. Условия реального участия и пробного занятия будут проверяться отдельными сценариями.

`volunteer_role` — редактируемый справочник видов помощи со стабильным ID, названием, описанием и версией. Создание и изменение метаданных сохраняются в `volunteer_role_revision` с автором и временем. Нормализованное название уникально без учёта регистра. Переименование не сбрасывает допуски; для другого вида деятельности создаётся новый ID. Начальных утверждённых направлений в миграции нет. Удаление и архивирование пока не реализованы.

`VolunteerClearanceReader.own()` определяет профиль по сессии и возвращает только публичную проекцию текущих решений. Оформление и допуски читаются в одной транзакции `REPEATABLE_READ`, без кэша в HTTP-сессии. В модели есть отдельные проверки `hasConfirmedPaperwork()` и `hasAdmission(roleId)`; это независимые факты, не универсальное разрешение ко всем данным фонда. При реализации материалов и записи на занятия потребитель должен явно проверить необходимые факты на сервере. Проверку допуска и запись участия нужно согласовать транзакционно с его отзывом — один ранее полученный снимок не гарантирует неизменность прав.

История решений доступна только координатору, последние 50 ревизий отображаются в интерфейсе. Волонтёр видит своё оформление и только те виды помощи, для которых уже принято решение; приостановка и отзыв сохраняются видимыми с пояснением. Внутренние заметки, авторы и аудит не входят в собственный ответ.

На этом этапе хранятся отметки координатора. Сканов, электронной подписи, автоматической проверки комплекта и сроков действия нет. Перечень документов, требования к видам помощи, правила пробы и обязательное обучение уточняются по материалам фонда. Уведомления об изменениях ещё не подключены.

## Доступный контракт приложения

`GET /api/v1/system/info` возвращает имя и версию приложения:

```json
{ "name": "volunteer-platform", "version": "0.1.0-SNAPSHOT" }
```

`GET /actuator/health/readiness` возвращает готовность приложения с проверкой PostgreSQL, без внутренних деталей. Регистрация, вход, сессия, CSRF и собственная анкета описаны в [контракте API](api.md). Остальные бизнес-маршруты закрыты конфигурацией Security.

## Открытые правила фонда

До реализации соответствующего сценария уточняем состав вводного и расширенного доступа, порядок пробы и оформления, условия допуска к ролям, обязательность учебных тем, самозапись, вместимость, отмены и подтверждение часов. Количество уроков, проходной результат и критерии допуска не выводятся из демонстрационных примеров. Материалы фонда будут подключаться на этапе обучения.
